You don't want four terminal windows. You want the migration done, the tests green and the docs updated, ideally while you get a coffee. The terminal windows are just the part that is in your way.

The agentic workspace in Personal Jarvis is built around that. One workspace holds up to **sixteen coding sessions**, each one a real CLI agent in its own terminal: Claude Code next to Codex next to OpenCode, all on the same screen. And because Jarvis is a voice assistant first, you can brief the whole row with one spoken sentence.

This post walks through how the grid is laid out, what actually happens between your sentence and sixteen typed prompts, and the few rules that keep it honest when something goes wrong.

## One workspace, many agents

A workspace lives inside a **project**, which is simply a folder you connected. The structure is three levels deep and never more:

Each session is a full CLI process with its own pseudo-terminal. That is why sixteen is the ceiling: it is a resource limit, not a layout preference. Past it, the source code's own advice is to open a second workspace.

The agents you can put in a pane today are Claude Code, Codex, Cursor CLI, OpenCode, Kimi Code, the GLM Coding Plan, Grok Build, Antigravity and DeepSeek Harness, plus a plain terminal for everything else. Jarvis doesn't replace these tools. It gives them a shared desk.

One thing to know before you start: **workspaces that share a folder share its files.** Two agents editing the same file will step on each other exactly as two people would. If you want real isolation, open the project's menu and pick **New workspace in a worktree**: its agents get their own folder and their own branch.

## How the grid decides its shape

You never pick a layout. The grid deals your panes into an even arrangement: side by side for two, two rows for up to eight, and one extra row per four sessions after that, never wider than four columns.

Two details matter more than they look:

- **Your terminal font never shrinks.** If the screen is too small for every pane at its minimum size, the grid scrolls instead. A 9-point terminal is not a feature.
- **Reordering is free.** Drag a pane by its header or press <kbd>Alt</kbd> + an arrow key. The pane moves, the agent inside keeps running. Nothing restarts, because a pane's identity is its session ID, not its position.

## One sentence, many prompts

Here is where the voice part earns its place. Say something like *"have all agents in the Refactor workspace add logging to their module"* and Jarvis does four things, in order:

<Figure fig="E" caption="The path of one spoken order. Composition is the slow step, so it runs in parallel, five at a time." source="docs/igentic-workspaces.md, fanout.py">
  <Flow
    steps={[
      { tag: "01 · Inspect", title: "Read the project graph", note: "the same tree the sidebar shows, with live status" },
      { tag: "02 · Resolve", title: "Find the exact targets", note: "names, IDs, or the active workspace; asks back if two match" },
      { tag: "03 · Compose", title: "Write one prompt per agent", note: "a proper brief, not your raw sentence", hero: true, fan: 5 },
      { tag: "04 · Deliver", title: "Type it into each terminal", note: "every pane returns its own verdict" },
    ]}
  />
</Figure>

Step three is the interesting one. Jarvis doesn't paste your sentence into sixteen terminals. It composes a real brief for each agent with a stronger model, because the agent will work from that prompt for the next several minutes. The team measured that composition at **10 to 21 seconds per prompt**, and chose quality over speed on purpose.

That creates a problem. A spoken turn gives up after about 20 seconds. Composing eight prompts one after another cannot fit in any turn. So the prompts are composed in parallel, with at most five in flight so that a big fleet doesn't hit your provider with twenty calls at once and get rate-limited.

<Figure fig="F" caption="What parallel composition buys you. Arithmetic from the measured 10–21 s range at its midpoint (15 s), not a benchmark run. Five in flight means eight prompts take two waves." source="fanout.py, DEFAULT_CONCURRENCY = 5">

No API key at all? Every agent still gets briefed. The composer falls back to a deterministic prompt built from your words when no model is reachable, so the feature degrades instead of breaking.

## Honest about the partial result

The hardest part of talking to a fleet is not delivery. It is telling you the truth when delivery only half worked.

An early version looped over the panes and reported success when the loop finished. In one live session, one of two agents received the brief and Jarvis said both were working. The fix changed the shape of the result itself: a fleet order no longer has a single "ok". Every terminal comes back with its own verdict, and anything undelivered is said out loud.

<Figure fig="G" caption="What changed in how a fleet order reports back.">
  <Compare
    before={{
      title: "Before",
      items: ["One loop, one success flag", "First dead pane stops the rest", "“Both agents are working” when one is"],
    }}
    after={{
      title: "Now",
      items: [
        "One verdict per terminal",
        "A dead pane never blocks the others",
        "Undelivered panes are named in the reply",
        "A receipt means <em>delivered</em>, never <em>finished</em>",
      ],
    }}
  />
</Figure>

Two more guards sit around this:

- **The duplicate shield.** Voice models sometimes re-send an order, slightly reworded. If an order longer than 40 characters matches one from the last ten minutes at 90% similarity or more, it is treated as the same order instead of spawning a second fleet. Short steering words like "continue" are exempt, because you really do say those twice.
- **No guessing.** If "the docs agent" matches two sessions, Jarvis asks which one. Sends are recorded in a local database before they go out, so a reconnecting voice session can never replay an order by accident.

## Methodology

Figures in this post come from the Personal Jarvis source at version 2.3 (`jarvis/agentic_ide/session.py`, `fanout.py` and `docs/igentic-workspaces.md`). The grid layouts in Fig C are the output of the app's own layout function. Fig F is arithmetic on the composer time the team measured, not a timed benchmark; your numbers depend on the model you pick for prompt composition. The live multi-agent voice path has been exercised on Windows and a fresh headless Linux install; native macOS voice acceptance is still open.
