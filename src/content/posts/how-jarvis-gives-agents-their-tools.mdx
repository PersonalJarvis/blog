On the machine we build Personal Jarvis on, an agent can be handed 200 different tools. Two MCP servers bring 77 of them. Ask Jarvis about tomorrow's weather, and none of those 77 reach the model. Ask it to open a pull request, and 45 do.

Skills, plugins and MCP servers are three words that get mixed up a lot. In Jarvis they are three different things, and they all end up in the same place: one catalog that every agent takes its tools from. This post covers what each of the three is, how an agent gets its share, why a connected MCP server stays quiet until a request is about it, and what broke on the way.

## Three things, one catalog

- **A skill is text.** A short Markdown file, `SKILL.md`, that tells the assistant how to do one task: the steps, what to check first, when to ask. A skill cannot do anything on its own. It tells the model how to use the tools it has.
- **A plugin is a connection to a service.** GitHub, Notion, Slack, Google Calendar. Installing one means signing in once, and Jarvis keeps the sign-in in your system's keyring.
- **An MCP server is a program that offers tools in an open format**, the Model Context Protocol. Many apps can use the same server. You can add one yourself, and most plugins bring one along.

All three land in one place: the Plugins / Skills / MCP section of the app, with a tab for each.

38 of the 46 plugins carry an MCP server. Most of those are servers the service runs itself, such as GitHub's, Notion's or Linear's. So for most plugins, "installing a plugin" means: sign in once, and Jarvis connects to that service's MCP server with your sign-in. The other eight are tools built into Jarvis, like Google Calendar and Spotify, and the two chat channels Telegram and Discord.

Plugins are packaged in the open [Agent Plugins](https://agent-plugins.org/) format: a `plugin.json`, and an `mcp.json` when there is an MCP server. Everything only Jarvis needs, like the sign-in flow and the logo, sits in a separate section that other apps ignore.

A plugin's manual is short. This is the whole body of the GitHub one:

```md
Use the connected GitHub tools to inspect and act on the user's repos,
issues, and pull requests.

- Read-first: list/search issues or PRs before acting; reference items by number.
- Confirm before destructive/consequential actions (merging, closing).
- Summarize plainly: title, number, state, author. Keep raw ids out unless asked.
```

Its header names the plugin it belongs to, the words that point to it ("repo", "pull request", "issue", and their German forms), and its risk tier, `ask`. When you connect the plugin, those words start routing requests to it. When you disconnect it, they stop.

A skill finds its way into a turn in two ways. Its own words can match what you said, and a paraphrase counts too: a scorer reads the words the skill's author already wrote down and ranks every skill in about 75 microseconds, with no model call. Or the model asks for it by name.

Matching a skill is cheap. Letting it take over a turn is not, so Jarvis decides that from what the skill does, not from what it claims:

- A skill that only adds **instructions** may take over a turn by itself.
- A skill that uses **tools**, like every plugin manual, may join a turn only while the model can still decline it.
- A skill that **starts a background job** never fires by itself. You name it, or the model asks for it.

Skills from elsewhere work too. A `SKILL.md` written for Claude Code, Codex or Cursor installs in Jarvis, and the install dialog shows you its full text first, because the text is the skill. Jarvis keeps only its name, description and other descriptive fields. Anything that would grant behaviour, such as triggers, a lower risk tier or a background job, is dropped and listed on the skill so you can see what was ignored.

## MCP servers: add your own

You can add any MCP server in the MCPs tab, either one that runs on your machine or one at a web address. Jarvis checks that the server answers, lists its tools and switches it on.

An MCP server can hold a lot of tools. NotebookLM alone has 32: create a notebook, add a source, make flashcards, a mind map, a podcast. If every one of them went to the model on every turn, the list of tools would grow with each server you add, every turn would get slower and more expensive, and the model would be more likely to pick the wrong one.

## Connected does not mean offered

So before every turn, Jarvis checks each MCP server against what you just said. A server's tools are offered only if one of these holds:

- you name it ("NotebookLM", "notebook lm"),
- its usage card matches (GitHub's lists "pull request", "issue", "repo"),
- or a distinctive noun from its own tools appears in your request. NotebookLM's tool `flashcards_create` gives it the word "flashcards".

There is no model call in this check. It is plain word matching, so it costs nothing and works with any provider. We ran the shipped check over our catalog's 77 MCP tools for seven example requests:

Six of the seven requests get exactly what they should. The flight question gets nothing, which is the point: an earlier version offered NotebookLM's tools on a flight question, the model called one of them, and the turn lost about 35 seconds until the call timed out.

The issue question shows a gap we have not fixed yet. "Which issues are still open in the website repo?" rightly gets GitHub's 45 tools. It also gets all 32 of NotebookLM's, because one NotebookLM tool adds a website as a source, and so "website" counts as one of its words. The model can ignore them, but they are 32 tools it did not need.

## How an agent gets its share

Every agent in Jarvis takes its tools from the same catalog, in four steps on every turn:

1. **Grant.** By default an agent gets everything the global safety rules allow. You can narrow it to a short allow-list.
2. **Deny.** Anything you blocked for this agent is removed. So is every tool that is not connected right now. An agent never sees a tool that would only answer "not available".
3. **Focus.** The agent's main tools move to the top of the list, and the agent is told in its instructions that these are its own. The rest follow in a fixed order, so the list is the same on every turn and providers can cache it.
4. **Per turn.** The MCP check from above.

Focus is set once, when you create the agent, by matching its name and description against the catalog. No model is involved. Describe an agent as "a daily overview of my Gmail inbox", and it gets `plugin:gmail` as its focus. It keeps every other tool too, so it can still check the calendar or look something up in the wiki.

That agent exists on our machine. When we measured, its Gmail sign-in had expired, so for that moment the agent had no Gmail tools at all. That is on purpose: a tool that cannot work is not offered. The Plugins tab shows the sign-in under "Needs attention" until it is renewed.

Some tools never reach any agent: the tools that start background workers, switch providers, add MCP servers or control the app. An agent can do work. It cannot hire more workers or rebuild the house it lives in.

Agents also write skills of their own. When an agent finishes a task and a repeatable procedure came out of it, Jarvis writes that procedure down as a skill in the agent's own folder. It is active for that agent right away, and you can promote it to all of Jarvis, where it starts as a draft. Our agents have written 8 so far.

## MCP in the other direction

Jarvis does not only use MCP servers. It is one, twice.

- **For its own agents.** An agent can run on a Claude Code or Codex subscription instead of an API key. That CLI brings its own shell and editor, and it reaches Jarvis' tools over MCP, through a server Jarvis runs for that session. The same approval rules apply.
- **For other apps.** Claude Desktop, Cursor, VS Code, Codex or a second Jarvis can connect to your team over MCP. Twenty-four tools let them see the agents, talk to one, post a job without naming who should do it, and answer approval requests. Each app gets its own key, and nothing that needs your approval gets past it.

## What broke on the way

- **The NotebookLM flight question.** A connected MCP server used to be offered just because it was connected. A plain flight question once called `notebooklm-mcp/chat_configure` and waited about 35 seconds for it. The fix is the check described above, with a list of generic words like "create", "list" and "report" that never count as a signal.
- **"repo" inside "report".** The GitHub skill's pattern once fired on "report" and "reporter". Word boundaries in the pattern fixed it. The calendar skill had the same problem with the German word "Termin" inside "Terminals".
- **One spelling let spawn tools through.** The list of tools no agent may have was written as `spawn-worker`, while the tools register as `spawn_worker`. For a while that mismatch let every spawn tool into agents' lists. The list now matches either spelling.

## If you use Jarvis

- **Install the plugin, not just the MCP server.** A plugin brings the sign-in and the manual. A bare MCP server brings only the tools.
- **Name the service when it matters.** "In NotebookLM, make flashcards" always reaches it, even when your wording would not.
- **Describe an agent by what it owns.** A description that names the service, like Gmail or GitHub, sets the agent's focus at no cost.
- **Watch "Needs attention".** An expired sign-in silently takes those tools away from every agent until you renew it.
- **Read a skill before you install it.** The install dialog shows the full text. That text is all the skill is.

The rules behind this post are written down in the repository: [the agent definition](https://github.com/PersonalJarvis/PersonalJarvis/blob/main/docs/agent-society/agent-definition.md), [portable skills](https://github.com/PersonalJarvis/PersonalJarvis/blob/main/docs/marketplace/portable-skills.md), [the plugin format](https://github.com/PersonalJarvis/PersonalJarvis/blob/main/docs/marketplace/agent-plugins-standard.md) and [the agent MCP surface](https://github.com/PersonalJarvis/PersonalJarvis/blob/main/docs/agent-mcp.md). If a tool shows up where it should not, or stays away when it should come, open an issue on [GitHub](https://github.com/PersonalJarvis/PersonalJarvis/issues).
